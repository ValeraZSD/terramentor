# Interface languages

The interface — every label, button, hint, toast and dialog the app itself
writes — is translatable. Settings → General → *Language* picks one; the
default follows the browser. Lessons, questions and the tutor are a different
thing: their language is a property of each project (`content_language`) and
was multilingual before the interface was.

Shipped: English (the source) plus German, Spanish, French, Italian,
Japanese, Dutch, Polish, Portuguese, Russian, Ukrainian and Chinese. **Every
language other than English is a first pass written by a model.** Corrections
are the most useful small contribution this project can take: a language is
one file, and fixing a sentence is a one-line change.

## Fixing a translation

`src/locales/<code>.json` maps the English text to the translation:

```json
"Mark done anyway": "Toch als klaar markeren",
"{{count}} cards still due_one": "Nog {{count}} kaart",
"{{count}} cards still due_other": "Nog {{count}} kaarten",
```

Edit the right-hand side. Keep every `{{placeholder}}` exactly as it is — it
is filled in at runtime, and a renamed one prints literally. A key ending in
`_one` / `_few` / `_many` / `_other` is a plural form; the suffixes are the
plural categories your language has (Intl's rules), and each one is a separate
entry. Run `node tools/i18n-gates.mjs` — it checks placeholders, plural forms
and that no entry is stale — and open a pull request.

## How this app addresses its reader

Every language here chooses between addressing the learner formally or
informally, and the choice has to be made once for the whole file rather than
per sentence. It is not a matter of taste: a file that says *du* on one screen
and *Sie* on the next reads as though two people wrote it, and that is exactly
what a model produces when it translates two thousand strings in batches of forty with
no memory between them — the first German pass came back 147 informal against
145 formal.

| language | addresses the reader as |
|---|---|
| German | `du` — never `Sie` |
| Dutch | `je` / `jouw` — never `u` |
| French | `vous` — never `tu` |
| Spanish | `tú` — never `usted` |
| Italian | `tu` — never `Lei` |
| Portuguese | `você` |
| Polish | informal — never `Pan` / `Pani` |
| Russian | `вы`, lowercase — never `ты` |
| Ukrainian | `ви`, lowercase — never `ти` |
| Japanese | polite です / ます |
| Chinese | 你, not 您 |

The split is per-language convention rather than a policy: French and Russian
software says *vous* / *вы* where Dutch and German say *je* / *du*. The table
lives in `ADDRESS` in `tools/i18n-translate.mjs`, so a model filling a new
locale is told which one to use, and `node tools/i18n-translate.mjs de
--register` re-translates only the entries that drifted to the other form —
a whole-file `--redo` would throw away every correct translation to fix a
tenth of them.

## The app does not know who is reading it

English agrees with nobody, so *Got it, continue* and *You proved this* reach a
Slavic or Romance translator as a choice English never had to make — and a model
picks the masculine every time. The first pass answered the tutor in Russian
with *Понял*, told a Polish reader *Udowodniłeś to*, and promised a Spanish one
*Seguirás conectado*: an app that is wrong about its reader on the first screen
they see.

A neutral wording always exists, and it is not a slash or a bracketed *(a)* —
those are what a form asks for, not what software says. It is an impersonal or
passive form (*Potwierdzone {{count}} dni temu*, *Przejrzano wszystkie fiszki*),
a noun (*Wynik: {{score}}*), a present tense (*Jak dobrze to znasz?*), or a
different subject altogether (*La sessione resterà attiva* for *You'll stay
signed in*). Russian and Ukrainian address the reader as *вы* / *ви*, which is
plural and therefore already neutral — what is left there is the copy the reader
*speaks*: a button that answers the tutor, a filter that says what I missed.

`node tools/i18n-audit.mjs <code> --list` reports the ones that slipped, under
`gender`, and the translator's prompt carries the rule so a new locale does not
arrive with it.

## Reading a locale the way a speaker would

`npm run i18n:audit` (or `node tools/i18n-audit.mjs <code> --list`) reports
what is probably wrong. It is the companion to `i18n-gates.mjs` and the
division between them is deliberate: the **gate** asserts what must never ship
— a dropped placeholder, a key the source stopped using — and fails the build;
the **audit** reports a judgement and fails nothing, because "wrong wording" is
not something a build should hold an opinion about.

It looks for the register mix described above, wordings that assume the reader
is a man, values left identical to the
English, Latin text stranded inside a non-Latin script, translations far longer
than the control they sit in, lost ellipses and terminal punctuation, and
**collisions** — two different English labels that came back as the same word.
That last one is how the French build shipped a navigation bar with two tabs
both reading *Calendrier*: nothing was missing, nothing was misspelt, and the
reader had no way to tell *Calendar* from *Schedule*.

A term the model gets wrong is usually wrong everywhere it appears, and the
worst of them sit on the screen the learner sees most. Corrected by hand in the
first pass, as examples of the kind: Polish *Kartki* ("sheets of paper") for
flashcards, which are *fiszki*; Italian *Carte*, which is paper or a playing
card; German using *Karten* in the plural and *Karteikarte* in the singular for
one thing; Ukrainian *Огляд* ("a survey") for a spaced-repetition review, which
was also its translation of *Overview*; Ukrainian *Гаразд* ("alright") as one
of the four rating buttons, which have to agree with each other in both meaning
and part of speech.

## Adding a language

1. Add it to `LANGUAGES` in `src/i18n/index.ts` with its native name.
2. Create `src/locales/<code>.json` — either by hand from `en.json`, or with
   `node tools/i18n-translate.mjs <code>` against any OpenAI-compatible model
   (the local llama-swap by default; `AI_BASE_URL`/`AI_MODEL`/`AI_API_KEY`
   otherwise). The tool fills only what is missing, rejects any translation that
   loses a placeholder, and writes after every batch, so it can be interrupted
   and resumed.
3. `node tools/i18n-gates.mjs` must pass; its coverage table says how far the
   file is.

Right-to-left languages: `dir="rtl"` is set on the document for `ar`, `he`,
`fa`, `ur`, but no layout has been checked in that direction yet.

## How it works, for people changing the app

**The key is the English text.** `t('Mark done anyway')` reads as what it
renders, a missing translation falls back to a sentence rather than to
`feed.checkpoint.markDone`, and the extraction could rewrite 1,900 call sites
without anyone inventing 1,900 names. The cost is that rewording an English
string orphans its translations — `tools/i18n-gates.mjs` reports the orphans
so a reword is a visible chore rather than a silent regression.

Writing new UI:

- In a component, `const { t } = useTranslation()` and `t("…")`. Placeholders
  are `{{name}}` with an options object: `t("{{count}} cards due", { count })`.
  Passing `count` makes the key plural; `en.json` then carries `_one` and
  `_other` forms (the extractor generates them; fix the singular by hand).
- Outside a component (a utility, a module-level table), use `i18n.t(…)` at
  call time, or tag the string with `k("…")` in the table and `t(row.label)`
  where it renders. `k()` is identity at runtime; it exists so the tools can
  see the key.
- Dates and numbers go through `src/utils/locale.ts`, never a literal locale.
- After adding keys, `node tools/i18n-extract.mjs` refreshes `en.json` from
  the source (it is idempotent: a file already using `t()` is left alone).
  `node tools/i18n-extract.mjs --report` lists what it will not touch — text
  inside `<code>`, runs mixing text and complex expressions.

What is deliberately not translated: text the **server** writes into a
response (a failure record's plain-English cause, a feed notice, an API error
message). Those belong to a code-plus-parameters contract between server and
client, not to string replacement on the client, and are the next boundary.
