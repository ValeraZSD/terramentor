the way a newcomer meets the project: clone, `npm install`, `npm test`, `npm run build`,
`npm run check`, then start the app on an empty library and use it. No code was changed.

## R1. Login lockout bypassed by rotating `X-Forwarded-For`; one loopback caller locks out the owner (security, confirmed)

**Where**
- `server/app.js:100`: `app.set('trust proxy', 'loopback')`.
- `server/auth.js:276-297`: the throttle is a per-`req.ip` `Map` (8 failures, then 15 minutes locked).
- Used per IP by `server/routes/auth.js:59` (pair), `:74` (login), `:104` (setup) and `server/routes/devices.js:55-58`.

**Steps**, against a scratch server with the password `correcthorse`:

```bash
B=localhost:3402; H='-H Content-Type:application/json'
for i in $(seq 1 9); do curl -s -o /dev/null -w '%{http_code} ' -XPOST $B/api/auth/login $H -d "{\"password\":\"bad$i\"}"; done
# 401 401 401 401 401 401 401 401 429        <- the throttle works for a fixed IP
for i in $(seq 1 12); do curl -s -o /dev/null -w '%{http_code} ' -XPOST $B/api/auth/login $H -H "X-Forwarded-For: 10.9.8.$i" -d "{\"password\":\"bad$i\"}"; done
# 401 401 401 401 401 401 401 401 401 401 401 401   <- never 429
curl -s -XPOST $B/api/auth/login $H -H "X-Forwarded-For: 10.9.7.1" -d '{"password":"correcthorse"}'
# {"ok":true}
```

**Impact**
- Because loopback is a trusted proxy, any caller on a loopback socket picks its own `req.ip` and gets a fresh 8-guess budget every time. That covers local processes and anything relayed through a header-preserving tunnel (`ssh -L`, socat, an editor's port forward). The only limit left is scrypt's cost, about 16 guesses a second.
- `server/devices.js` treats a set password as meaning local processes are not trusted, so this matters.
- The reverse also happens. Eight bad logins without the header lock out every loopback client for 15 minutes, the owner's browser included. Under Docker every client arrives from the bridge address, so one bad actor locks everyone out.
- The `attempts` map is never pruned, so rotating addresses also grows it without bound.

**Fix:** add a global failure counter or backoff alongside the per-IP one, and cap or evict the map.

## R2. `/api/auth/change` and `/api/auth/disable` check the password with no lockout (security, confirmed)

**Where:** `server/routes/auth.js:125-131` and `:144-149` call `checkPassword` directly. Neither calls
`loginBlocked` or `recordLoginFailure`, which `passwordRefused` in `server/routes/devices.js:55` does.

**Steps:** log in, then:

```bash
for i in $(seq 1 15); do curl -s -b cj -o /dev/null -w '%{http_code} ' -XPOST $B/api/auth/change $H \
  -d "{\"currentPassword\":\"g$i\",\"newPassword\":\"newpassword123\"}"; done
# 401 ×15, never 429
curl -s -b cj -XPOST $B/api/auth/change $H -d '{"currentPassword":"correcthorse","newPassword":"newpassword123"}'
# {"ok":true}
```

**Impact:** anyone holding a session or a device cookie can brute-force the password with no limit. Devices are paired by QR and their cookie lasts 400 days, so a lost phone is enough. With the password they can:
- change it, which signs out every other session and removes every other device;
- turn the password off;
- mint an API key.

**Fix:** put both checks behind the same throttle as login.

## R5. "Today" is the UTC date, not the learner's (bug, confirmed)

**Where**
- Server:
  - `server/scheduling.js:198-200` (`today()` is `formatDate(new Date())` in UTC)
  - `server/feed.js:134`, `server/today.js:189`, `:499`, `:671`
  - `server/routes/schedule.js:126`, `server/routes/insights.js:36`, `server/routes/studyDashboard.js:22`
  - `server/projectState.js:110`, `server/dailyPlan.js:22`
  - `server/studyTime.js:65`, `server/completion.js:113`
- Client: `src/utils/tree.ts:377-386` (`todayStr()` from `getUTC*`), used by the calendar, timeline, sidebar and schedule modal.
- Header: `src/components/feed/FeedHeader.tsx:54-56`, which formats the server's date with `timeZone: 'UTC'`.

**Steps**
- At 13:14 UTC on Monday 26 October, open the app in a browser set to `Pacific/Auckland`, where it is 02:14 on Tuesday 27 October. The feed header says **"Monday, October 26"**:
  ```js
  // Playwright
  const ctx = await browser.newContext({ timezoneId: 'Pacific/Auckland' });
  // browser local time: Tue Oct 27 2026 02:14:21 GMT+1300
  // header line: Monday, October 26
  ```
- West of UTC it runs the other way. In New York at 21:00 on a Friday the app is already on Saturday: the day's plan, the study-week check and "studied today" all move to the next day mid-evening.

**Impact**
- For everyone outside UTC, the app's day starts at a clock time that isn't midnight.
- The topic due "today", what counts as overdue, the Mon–Fri study week and the day's study-time ledger are all off by a day for part of every day.
- The assistant is told the learner's real local date and time zone (CHANGELOG 1.2), so it and the feed can disagree about which day it is.
- `docs/ARCHITECTURE.md:166` sets the rule that dates are parsed as UTC midnight. That rule is right for *parsing* a `YYYY-MM-DD`, but it was also applied to *choosing* today's date.

**Fix:** derive today's `YYYY-MM-DD` from the learner's local calendar (the client sends it, or its time zone is stored), and keep the UTC-midnight parsing.

## R6. The test that `safeFetch` re-vets redirects passes when callers bypass it (test pins nothing, confirmed)

**Where**
- Test: `tools/security-gates.mjs:309-311` only checks that the text `redirect: 'manual'` appears in `safeFetch`. The behavioural redirect tests (the `tools/fixtures/redirect-credentials.mjs` fixture and `dns-pinning-gates`) never pass `redirect: 'follow'`.
- Guarded code: `server/netSafety.js:293` (`undiciFetch(url, { ...hopInit, redirect: 'manual', dispatcher })`).
- Real callers that do pass `redirect: 'follow'`: `server/ai.js:1982`, `server/appUpdate.js:159`, `:197` and `:415`.

**Steps:** swap the spread order so a caller's option wins:

```diff
- undiciFetch(url, { ...hopInit, redirect: 'manual', dispatcher })
+ undiciFetch(url, { redirect: 'manual', ...hopInit, dispatcher })
```

**Result**
- `security-gates` still passes, 380 of 380.
- `dns-pinning-gates` gives the same result as without the change.
- A direct probe of the changed `safeFetch` with `redirect: 'follow'` returned `200 INTERNAL` from the redirect target and never consulted `allowRedirect`. The unchanged code throws `refused a redirect`.

**Impact:** the SSRF guard's per-hop check and credential stripping can be undone by a one-token reordering, and nothing fails.

**Fix:** add a behavioural case that calls `safeFetch(url, { redirect: 'follow' })` and asserts the hop is still vetted.

## R7. DNS rebinding through a `.local` name reaches a library with no password (security, suspected)

**Where**
- `server/originGuard.js:75` treats every `*.local` host as a name nobody else can point elsewhere.
- `:163-168` passes an Origin equal to that Host.
- `server/auth.js:311-320` treats a loopback socket as the owner.

**What was reproduced (server side only):** with no password set,

```bash
curl -s -H 'Host: attacker-printer.local:3202' -H 'Origin: http://attacker-printer.local:3202' \
     -H 'Sec-Fetch-Site: same-origin' http://127.0.0.1:3202/api/projects
# []   (allowed; Host: evil.example is 403)
# the same headers on POST /api/auth/setup {"password":"…"} -> {"ok":true}
```

**What was not reproduced:** the browser half, which needed an mDNS responder.

**Why it is plausible:** mDNS names are answered by whoever on the LAN replies first. A LAN peer can answer `x.local` with its own address, serve a page, then answer with `127.0.0.1`. The page is then same-origin with the app, its requests arrive from loopback, and with no password set it can read the library, write to it and set a password. The comment at `originGuard.js:29-30` assumes `.local` cannot be rebound. Corporate `.local` AD zones have the same problem.

**Fix:** do not accept a DNS name ending `.local` as the Host of a request arriving on a loopback socket, or require the name to resolve to this machine.

## R11. Unauthenticated callers get a 25 MB JSON body parsed before the password check (security, low, confirmed)

**Where:** `server/app.js:164` (`express.json({ limit: '25mb' })` in the head middleware) runs before
`app.use('/api', requireAuth)` at `:321`.

**Steps:** with a password set and the server reachable from another address (`HOST=0.0.0.0`, Docker or a tailnet), POST a 15.7 MB JSON array to `/api/projects` with no credentials:
- the answer is `401`, after 0.24–0.36 s every time;
- an empty body gets its `401` in 0.002 s.

**Impact:** each request costs about 250 ms of event-loop parsing before it is refused, so a few in parallel stall the server for everyone. `app.js:148-150` already applies this reasoning to the origin guard, but not to auth.

**Fix:** a small-limit parser for the public auth routes, and the 25 MB one after `requireAuth`.

## R17. Origin check behind `tailscale serve` accepts any local-hostname Origin (security, low, suspected)

**Where:** `server/originGuard.js:188`. When the request carries `X-Forwarded-Proto`, any Origin whose
host is "local" passes. `tailscale serve` adds that header to every request it relays, so behind it
`Origin: http://192.168.1.5:8080` is accepted.

**Reproduced:** on loopback, `curl -H 'Origin: http://192.168.1.5:8080' -H 'X-Forwarded-Proto: http' -X POST …/api/auth/logout` returns 200.

**Not reproduced:** a browser exploit. Current browsers send `Sec-Fetch-Site`, and `isOwnFetch` still refuses on that. Older Safari (before 16.4) combined with Tailscale-identity access is the case where a LAN page's cross-site write would get through.

**Fix:** only honour this branch when the Origin host matches the forwarded or real Host.

## Checked and found sound

- **Remote access with `HOST=0.0.0.0` and no password:**
  - every `/api` route answers 401 `setupRequired`;
  - a spoofed `X-Forwarded-For: 127.0.0.1` from a remote socket is ignored;
  - a non-local `Host` is refused 403;
  - the public routes disclose only status, desktop status, the manifest and the icons.
- **Tailscale identity** (`server/devices.js:291-382`) needs all of: a loopback socket, exactly one tailnet hop, a `.ts.net` Host matching this machine, and `tailscale whois` agreeing.
- **Secrets and cookies:**
  - the setup code is 48 bits and throttled; pairing codes are single-use with a 10-minute TTL;
  - comparisons are timing-safe and passwords are hashed with scrypt;
  - tokens are HMAC-signed and rotated on a password change;
  - cookies are `HttpOnly` and `SameSite=Lax`, and `Secure` over HTTPS.
- **CSRF:** `Origin: null`, `Sec-Fetch-Site: cross-site` and `same-site`, and a different port are all refused. There is no CORS reflection unless `ALLOWED_ORIGINS` is set.
- **SQL:** every dynamic `db.prepare` template splices only code-side fragments or `?` lists. A fuzz of 239 routes with type-confused bodies found the 500s in R15 and nothing worse.
- **Paths:**
  - blobs are addressed only by `^[a-f0-9]{64}$` hashes taken from database rows;
  - Anki, bundle and library zips are read in memory and never written to disk under their own entry names, so there is no zip-slip;
  - library entries must match `^projects/[^/\\]+\.studyvault$`;
  - `precompressedStatic` stays inside `dist/`.
- **Stored XSS through files:**
  - media types are sniffed and SVG is refused;
  - document originals are served with a fixed MIME table;
  - chat attachments carry a sandbox CSP, and anything that isn't an image is downloaded rather than shown.
- **SSRF:**
  - captured links, link checks, the curator and web context all go through `safeFetch`, which pins DNS, re-vets every hop and blocks private, mapped and NAT64 ranges;
  - model, SearXNG and Ollama addresses are owner-configured and reachable only behind the gate;
  - the provider key goes only to the origin it was saved for.
- **Course export and re-import:** round-trips cleanly and warns about the duplicate.
- **Using the app:**
  - the welcome screen, every top-level page and the project views raise no console errors on a fresh library;
  - the feed degrades gracefully when the model's answers fail its checks;
  - scheduling a course over a 4-week window allocates every topic.
