# Architecture

How this system is put together, and why it is put together that way. If you are
looking for an exhaustive list of endpoints and columns, that is
[TECHNICAL_DOCUMENTATION.md](../TECHNICAL_DOCUMENTATION.md); if you are looking
for what the product is *for*, that is [CoreIdea.md](../CoreIdea.md). This
document is the middle layer: the shape of the system and the decisions that
hold it in that shape.

---

## 1. The one-sentence version

A learner's curriculum is a tree of topics; the engine schedules that tree
against a deadline, writes and serves the teaching itself, measures what has
actually been learned, and resurfaces what is fading, with every model call
optional and the library on the learner's own machine.

## 2. The loop is the architecture

Almost every module is a stage of one cycle, and the cleanest way to read the
codebase is to walk it:

| Stage | What happens | Where it lives |
|---|---|---|
| **Discover** | A curriculum comes into existence: authored by hand, generated by a model, imported as JSON or a `.studyvault` bundle, brought in as an Anki deck (`.apkg`, with its media and review history), or captured ad-hoc into the Inbox. | `routes/createProject.js` creation pipeline, `agentic.js`, `ankiImport.js` + `decks.js`, `capture.js` |
| **Plan** | The tree's leaves are weighted and allocated across the study window, deadline-first. | `scheduling.js` |
| **Study** | The learner reads, answers, practises. The home page is a card stream, not a dashboard. | `feed.js`, `feedGen.js`, `courseContext.js`, `paper.js`, `studyMaterial.js` |
| **Prove** | A topic counts as proven only on evidence: a quiz, a mastery check, a worked page. | `mastery.js` |
| **Remember** | Proven topics decay on a schedule and come back as recall questions (*ghost questions* in the code) and FSRS reviews. | `mastery.js`, `dailyPlan.js`, `src/utils/srs.ts` |

Two cross-cutting layers sit underneath all five:

- **The semantic layer** (§6): embeddings over material *and* over the
  curriculum, which is what lets the engine relate a topic to anything other
  than its own parent.
- **The quality layer** (§7): the gates every AI-authored artifact passes
  before a learner sees it.

## 3. Process shape

One Node process, one SQLite file, one optional model endpoint.

```
   browser ──HTTP/SSE──▶  Express (server/app.js + routes/)
                              │
              ┌───────────────┼────────────────┬─────────────────┐
              ▼               ▼                ▼                 ▼
        better-sqlite3   task queue      vector chain      model endpoint
        (synchronous)    (tasks.js)      (embeddings.js)   (Ollama / OpenAI-
              │          1 local/3 hosted serial, shared    compatible)
              ▼                           with nodeEmbeddings
     terramentor.db
     (WAL, foreign_keys=ON)
```

The HTTP layer is three parts: `server/routes/`, one file per area of the API;
`server/app.js`, whose `createApp()` mounts those files' routes in one ordered list
without opening a port; and `server/index.js`, which listens and starts the
background work. Where a new route goes, and why the mount order matters, is in
[TECHNICAL_DOCUMENTATION.md §8](../TECHNICAL_DOCUMENTATION.md#8-api-surface).

`better-sqlite3` is **synchronous**, which is the single most load-bearing fact
about the backend. There is no connection pool, no transaction interleaving and
no `await` between a read and the write that depends on it, so a whole class of
race condition simply cannot occur. The cost is that any long CPU loop blocks
every other request, which is why the two places that do real computation
(`atlas.js`, the embedding indexers) yield to the event loop explicitly rather
than running to completion.

### Four ways to run the same process

The process above is the whole product in every deployment; what differs is
who starts it and where its files are. `server/paths.js` is the one place that
decides the second question (`DB_PATH`/`VAULT_ROOT`, else `DATA_DIR`, else
the historical `server/` layout), and nothing else in the server knows which
shape it is in, enforced by `tools/tenancy-gates.mjs`, which fails a module
that reads those variables itself or names a data directory beside its own
source. A module that answers either question for itself is easy to write, and
the mistake is invisible in a checkout, where every answer happens to be
`server/`; it surfaces in a packaged install, where the application folder is
unwritable and is replaced on update.

| shape | started by | data | what is different |
|---|---|---|---|
| checkout (`npm run dev`) | Vite + `node server/index.js` | `server/terramentor.db`, `server/vault` | API-only; Vite proxies `/api` |
| standalone (`npm run standalone`) | `node server/index.js` | same | serves `dist/` on one origin; https if `.certs`. `standalone:watch` rebuilds on change and the open page reloads onto it |
| desktop (`desktop/launcher.js`, the zip) | the launcher, in-process | per-user app-data via `DATA_DIR` | `TERRAMENTOR_DESKTOP=1` mounts `server/desktop.js` (heartbeat self-stop, quit, data folder); `PORT_FALLBACK=1`; a Chromium `--app` window |
| Docker | the image's `CMD` | the `terramentor-data` volume via `DB_PATH`/`VAULT_ROOT` | `HOST=0.0.0.0` inside, published to loopback |

A hosted, multi-tenant deployment is a fifth shape that does not exist yet, and
it is deliberately a second PROCESS per learner rather than a second connection:
the database handle is opened once at module load and imported directly by most
of the server, so a tenant is a process started with its own `DATA_DIR`. A supervisor that maps an account
to its process reuses this table's fourth row instead of rewriting the server.
`tenancy-gates.mjs` boots two processes with two `DATA_DIR`s and checks they
share no path, so that option stays open by measurement rather than intent. The
identity question, one account per person against a single-user auth gate
designed for one owner, is the one this table does not answer. Details of the
desktop shape: `docs/DESKTOP.md`.

### Three background lanes, deliberately separate

A single queue would be simpler and would be wrong: these three workloads have
different latency contracts and would starve each other.

| Lane | Runs | Contract |
|---|---|---|
| `tasks.js` FIFO (as many at once as `aiConcurrency()` in `ai.js` allows: 1 for Ollama or a local, LAN or tailnet endpoint, 3 for a hosted API, `AI_CONCURRENCY` overrides both) | Chat, quiz, flashcards, project creation | The learner is *waiting*. Nothing slow may get in front. |
| The vector chain (`embeddings.js`) | Document indexing, topic-embedding sweeps | Nobody is waiting. Must never block the assistant. |
| `feedGen.js` | Lesson/question pre-generation | Runs *ahead* of the reader, and yields to any interactive task before every model call. |

Three smaller jobs follow the same rule on serial chains of their own, each
yielding to interactive work: `bulkGen.js` (bulk mastery checks and cards),
`pdfRecovery.js` (math recovery for uploaded PDFs) and `mediaDescribe.js`
(vision descriptions of card images).

Every task on any lane records its **origin** — the surface it was started from
(the assistant, a topic's Overview, a feed card, Settings) or, for the
app's own work, which job started it — as ids and a closed vocabulary
(`tasks.js` `normalizeOrigin`). The dock's record says it in words and opens it.
Visual builds that nobody pressed for are judged by `visualBuilds.js` (kind
switched off, model gate, a failure this model already had).

The vector chain is shared between `embeddings.js` and `nodeEmbeddings.js` on
purpose: a local model is usually single-slot, so a second chain would not add
throughput, since it would interleave a curriculum sweep into the middle of a large
PDF upload.

## 4. Data model

```
projects ─┬─▶ nodes (recursive: parent_id) ─┬─▶ resources
          │                                 ├─▶ documents ─▶ document_chunks ─▶ vec_chunks
          │                                 ├─▶ quizzes ─▶ quiz_attempts
          │                                 ├─▶ flashcards            (FSRS-6)
          │                                 ├─▶ node_mastery          (BKT + transfer)
          │                                 ├─▶ mastery_evidence
          │                                 ├─▶ feed_items            (teaching cache)
          │                                 ├─▶ paper_attempts
          │                                 └─▶ node_embeddings ─▶ vec_nodes
          └─▶ (settings, search_providers, widget_builds, chat_conversations ─▶ chat_messages are global)
```

Four conventions matter more than the tables:

**A node is the unit of everything.** Lessons, questions, flashcards, mastery,
paper attempts and vectors all key on `node_id`. This is why ad-hoc capture is a
*node in a permanent Inbox project* rather than a new entity type; it inherits
the entire loop for free.

**Notes are content, not structure.** A node with `is_note = 1` is teaching
material attached to a topic. It is never scheduled, carries no status and has
zero weight, so a **leaf is a non-note node with no non-note children**, and a
topic whose only children are notes is still a leaf. A leaf is not automatically
*work* either: the slices an Anki import cuts out of card order are leaves that
carry cards and are never taught, so everything that counts, plans, schedules or
teaches uses the *work* leaf. The rule is written twice, once on each side of the
wire; the names of both mirrors and the guard that holds them together are in
[TECHNICAL_DOCUMENTATION §2.2](../TECHNICAL_DOCUMENTATION.md#22-conventions-that-are-load-bearing).

**Integer ids are internal, uuids are for boundaries.** Every project, node,
resource and flashcard carries both. FKs, joins and URLs use the integer; the
uuid exists only for things that cross a device or marketplace boundary, where two databases'
autoincrement ids would collide. A uuid is never a join key. Questions carry one
too, although they have no row of their own. A course file carries all of them out
and back in, which is what a later edition needs to update a course in place
instead of installing beside it. How each is stamped:
[TECHNICAL_DOCUMENTATION §2.2](../TECHNICAL_DOCUMENTATION.md#22-conventions-that-are-load-bearing).

**Dates are `YYYY-MM-DD`, parsed as UTC midnight, always.** Local-time parsing of
a date-only string silently shifts a day depending on the reader's timezone.

## 5. The gate: how a topic closes

`skipped` is a first-class status. It means "I moved on without proving it":
it counts as *closed* for progress and pace, and is never a verified completion.
That honesty is the point of the whole Prove stage.

A leaf closes as proven on either of two clauses: the learner model's estimate
reached the threshold, or a real assessment of enough questions was passed at the
pass mark. The exact clauses, their constants and the three gate modes are in
[TECHNICAL_DOCUMENTATION §4.2](../TECHNICAL_DOCUMENTATION.md#42-the-gate); what
follows is why they have that shape.

The assessment clause keeps the gate honest to the score the learner saw. The
estimate alone would usually agree (a whole assessment is one batched
observation), but a seeded or long-decayed estimate can still sit below the bar
after a clear pass, and a pass the learner watched happen must count.

**Skip is always allowed, in every mode.** The app advises; it does not lock.
Practice evidence (flashcards, drills) sharpens the estimate and refreshes the
decay timer but can never satisfy the assessment clause: tuning an estimate is
not proving something.

How much one right answer is worth depends on the question's *format*, because
a coin-flip and a multi-step calculation are not the same evidence. So the
learner model's guess rate is read per format from the answer-format registry
(values in [TECHNICAL_DOCUMENTATION §4.1](../TECHNICAL_DOCUMENTATION.md#41-bkt)),
and the other two rates are fitted to the learner's own history once there is
enough of it.

## 6. The semantic layer

Two layers of vectors, doing different jobs, sharing one provider call, one vec0
table lifecycle and one background chain.

```
documents ─▶ chunks ─▶ vec_chunks   "find me material about X"   (RAG for the assistant)
nodes ──────────────▶ vec_nodes     "what else MEANS this?"      (transfer, atlas)
```

**`embeddings.js` (material).** Hybrid retrieval: FTS5 keyword search and
sqlite-vec KNN fused by Reciprocal Rank Fusion. Degradation is the design
constraint: without sqlite-vec or a reachable model, retrieval silently equals
plain FTS5.

**`nodeEmbeddings.js` (the curriculum).** One vector per non-note node, over
`parent title › title` + Overview. The project name is *deliberately excluded*:
it is the one string guaranteed to differ between two curricula teaching the same
thing, so including it would separate exactly the pairs this exists to find.

Freshness is **reconciled, not hooked**. Nodes are written from a dozen places, so
rather than a hook per call site a sidecar stores a hash of the exact text
embedded and the model that embedded it; a sweep re-embeds only the drift. A
clean sweep costs zero model calls, which is what makes it safe to fire from
every node write.

Two consumers:

- **`masteryTransfer.js`** seeds a topic's starting estimate from a proven twin
  in another project, so a learner who proved something once is not taught it
  from zero again. It can make the teaching shorter (`headStart.js`, shared with
  the placement probe) and it can never close a gate; the rules that hold that
  boundary are in
  [TECHNICAL_DOCUMENTATION §7.3](../TECHNICAL_DOCUMENTATION.md#73-mastery-transfer-servermasterytransferjs).
- **`atlas.js`**: the library drawn as one space, grouped into regions by
  meaning, on a flat map and on a sphere (the *Terra* view). Drawing it calls no
  model, so it draws identically every visit; only a region's *name* is a model
  enrichment, and it falls back to the region's most central topic. How it is
  laid out and kept bounded:
  [TECHNICAL_DOCUMENTATION §7.2](../TECHNICAL_DOCUMENTATION.md#72-atlas-serveratlasjs).

### The degradation contract

Every vector-only feature answers "unavailable" rather than "empty", and callers
must distinguish the two: a failed capability probe is not a verdict, and an
answer that never arrived must not be acted on. **Cache and act on an answer,
never on the absence of one.** Retrieval is the exception by design:
`searchDocuments` is hybrid and falls back to plain FTS5 keyword results when
the vector layer is down, so keyword results are valid output, not a degraded
state to discard.

## 7. The quality layer

Everything a model writes is treated as a draft. Five gates in `feedQuality.js`,
all failing *closed* toward serving less rather than serving wrong (the functions
behind each are listed in
[TECHNICAL_DOCUMENTATION §5.3](../TECHNICAL_DOCUMENTATION.md#53-quality-gates-feedqualityjs)):

1. **Mechanical**: unclosed fences, foreign-script leakage, ASCII art,
   deterministic arithmetic checks (`arithmetic.js`), and stripping the
   self-certifying "you can now…" closer models emit regardless of instructions.
2. **Answer-key verification**: a second pass answers the question *cold*,
   without the key; disagreement vetoes the card. Open questions can't be solved
   cold, so they switch to an arithmetic audit of the model's own explanation.
3. **Visual coherence**: the spec is read against the prose beside it, with
   *three* verdicts, not two: `wrong` removes the visual, but `text-wrong` means
   the picture was right and the prose is the mistaken half, so the lesson is
   rewritten instead. A binary version would have deleted accurate diagrams and
   shipped the false prose with its contradicting evidence gone.
4. **Audit of the teaching itself**: every other gate reads a question or a
   visual; this one reads every lesson part for false facts, self-contradiction,
   disagreement with earlier parts and a retraction left in the text, and
   recomputes the worked examples when the part has any. It calls a fact wrong
   only when it is certain, never when it merely cannot confirm one.
5. **Every other answer key**: a drill's prompt → answer items and a batch of
   generated flashcards are answered cold twice: once from the set's own pool
   of values (never shown the pairing), once with no pool at all, because a
   pool that lacks the right value pulls a checker toward a wrong one. A
   differing answer is not yet a dispute (another transliteration, × for x):
   it goes to one more look that sees both answers unlabelled, and only a key
   judged wrong there is removed
   (a drill with too few left, or too many wrong, goes whole). A paper
   exercise's reference solution is audited like an open answer, and a
   disputed one means no exercise.

A same-model second pass catches confusion, not a misconception the checker
shares with the author, so a check that passes is evidence, not proof.

Two principles generalise beyond this app:

- **A rejection must carry its reason into the retry.** Re-issuing an identical
  prompt at temperature 0.4–0.6 mostly reproduces the same draft with the same
  fault; the retry budget buys nothing. Faults are appended as a trailing
  instruction, because a constraint at the end of a long prompt is weighted more
  heavily than the same one earlier.
- **Hard defects vs soft weaknesses.** A defect means the card would *mislead*,
  and it is never served. A weakness means it works but measures less than it
  claims; a skipped question measures *nothing*, which is strictly worse, so it
  is served with the weakness recorded.

`feed_items` is a **cache**: changing a prompt does not improve rows already in
it. Re-author deliberately with `tools/feed-regen.mjs`, and measure with
`tools/feed-audit.mjs`. A new gate reaches stored rows only where the generator
re-reads them: lessons written before the fact audit and the drill check are
re-checked by a background tier (`pendingLessonCheck`), which fixes a drill in
place and has an unread part that fails the audit written again.

## 8. Frontend

React + TypeScript + Vite + Tailwind, Zustand for state, react-router for
navigation.

**The URL is the source of truth.** The store's navigation fields are only ever
written from the decoded URL, and every navigation action changes the URL rather
than the store. So back, forward, refresh, deep links and the phone's back gesture
all work without any of them being implemented. The one writer and the four
fields it owns:
[TECHNICAL_DOCUMENTATION §9.1](../TECHNICAL_DOCUMENTATION.md#91-routing).

**The interface is translated; the key is the English text.** `t("Mark done
anyway")` (react-i18next, `src/i18n/`), locale files in `src/locales/` loaded as
lazy chunks, `ui_language` applied before the first render. Content (lessons,
questions, the assistant) follows each project's `content_language` instead, and
text the server writes into a response is still English by design. `docs/I18N.md`.

**The home page is a feed, not a dashboard.** The algorithm decides what to
study; the learner scrolls, reads, answers, rates. Cards are appended and
deduped by key, never reordered, and consumed cards keep their size, so nothing
moves under the reader.

**Every screen must be good on a desktop and on a phone.** Input capability is
never inferred from width: a phone held sideways clears `sm:`, so keyboard hints
gate on `(pointer: fine)` and hover-revealed controls gate on the `can-hover:`
variant and also reveal on `focus-visible`. A control that only appears on hover
is unreachable by touch and by keyboard.

**AI-authored content renders through one pipeline.** Fenced specs
(mermaid / vega-lite / plot / smiles / math / animation / p5 / drill / widget) map to
dynamically-imported renderers; each renderer must *throw descriptive errors*,
because that text becomes the prompt for the one-shot repair loop. Prefer a
mechanical sanitiser over a repair round-trip, and persist a repair wherever the
visual lives; an auto-repairing card with no write-back re-runs the model on
every page load.

## 9. Privacy and trust boundaries

The product's central claim is that data stays on the machine, and the
architecture has to make that claim *checkable* (see [SECURITY.md](../SECURITY.md)):

- The server binds `127.0.0.1` by default; remote access is expected to go
  through a private overlay network rather than a forwarded port.
- An optional single-user password gate (scrypt + signed cookie, plus a bearer
  key for scripted clients) covers every `/api` route except sign-in itself, the
  desktop launcher's status probe and the app icon and manifest.
- Outbound traffic is the configured model endpoint (and the OpenRouter key
  exchange when you connect it), the search engines used while the AI drafts a
  project or when you press Find resources on a topic, the web lookups an answer
  makes when that switch is on (plus any hosted search engine you saved a key
  for), and the update check when you ask for one or turn the daily check on. All
  of it is visible in a packet capture; SECURITY.md enumerates it.
- **The one extension point runs no code.** Search providers are declarative
  manifests describing *what*; the host decides *how*. An extension system with
  host privileges would void the claim for every user, not just the one who
  installed the add-on, which is why real add-ons are still a design
  (`docs/ADDONS.md`) rather than a feature.

## 10. How to verify a change

The test bed is a set of deterministic guard suites, each driving the real
modules against a scratch database or a stub. None of them calls a model or the
network, so they run identically on a laptop and on a CI runner:

```bash
npm test                                # every suite; prints the live per-suite counts
npm run check                           # frontend types (tsc --noEmit)
node --check server/app.js              # (and any other server file)
```

`tools/run-gates.mjs` is what `npm test` runs, and CI runs the same command on
Node 22 and 24. Discovery is by filename, so a new `tools/*-gates.mjs` joins the
suite automatically. A selection of what they cover; the table is not the whole
list, `ls tools/*-gates.mjs` is:

| suite | asserts |
|---|---|
| `security-gates` | the origin/host guard, the markdown sanitizer schema, SSRF refusal |
| `feed-gates` | the feed's quality gates, option rules, deterministic arithmetic |
| `language-gates` | the gates still work in every offered content language |
| `srs-gates` / `fsrs-gates` | FSRS-6 scheduling, the SM-2 migration, the review log and optimiser |
| `mastery-gates` | Bayesian Knowledge Tracing, the batch update, fitted rates |
| `placement-gates` | the probe: stratified selection, section-bounded propagation |
| `head-start-gates` | a head start shortens the plan, brings the check forward and lightens the schedule |
| `mastery-transfer-gates` | transfer seeds a prior and can never close a gate |
| `node-embedding-gates` | topic vectors: reconcile, both sweeps, degrade to nothing |
| `atlas-gates` | the map is stable, bounded, finite, and its labels are placeable |
| `deck-gates` / `anki-gates` / `anki-export-gates` | deck structure, the five format traps, the export round trip |
| `import-gates` | the course-import boundary, and doc/validator field parity |
| `provenance-gates` | every AI-written row names the model that wrote it |
| `search-provider-gates` | the search-provider URL validator |
| `dep-gates` | package.json describes what the code imports, in both directions |
| `harness` / `anki-harness` / `vault-harness` / `dock-harness` | jsdom: real components, real events |

Six tools work on *your own* library rather than a fixture, so `run-gates.mjs`
excludes them: `leaf-invariant` (recounts every project's leaves independently
and checks the leaf rule), `feed-audit` and `feed-regen` (re-score or rebuild
cached feed content after a prompt change), `quiz-audit` (re-checks saved
questions), `fsrs-optimize` and `anki-refresh-text`. Two of them also call a
model (`feed-regen` the one configured in the app, `quiz-audit` the endpoint named
in its `AI_*` variables), and four can write to the library;
what each does is in its header and in
[CONTRIBUTING.md](../CONTRIBUTING.md#before-you-open-a-pr).

The frontend linters are advisory: they report findings for a human to judge,
which is why CI does not gate on them:

```bash
node tools/style-lint.mjs               # hardcoded colours, accent misuse
node tools/a11y-lint.mjs                # keyboard/screen-reader traps
node tools/contrast-audit.mjs           # WCAG AA in light and dark
```

The habit these encode: for anything a model writes, ship **both** a preventive
gate and a re-runnable auditor, and report before/after as numbers.
